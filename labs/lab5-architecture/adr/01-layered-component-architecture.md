# ADR-01: Шарувата компонентна архітектура FoodDelivery, межа системи та нотація Mermaid

* **Status:** Accepted
* **Date:** 2026-11-23

## Context
Для системи `FoodDelivery` необхідно зафіксувати компонентну архітектуру, яка об'єднує модель даних (`er_v2.mmd`, 9 сутностей), функціональні й нефункціональні вимоги (`FR-01`–`FR-08`, `NFR-01`–`NFR-05`), взаємодії (`UC_Checkout`) та процеси Завдань 1–4. Потрібно визначити рівень декомпозиції внутрішніх сервісів, межу системи (`System Boundary`) та нотацію для відображення `provided`/`required`-інтерфейсів.

## Decision Drivers
* Повна трасованість усіх компонентів до 9 таблиць `er_v2.mmd` і класів Завдання 3 (`OrderController`, `OrderRepository`, `PromoService`, `NotificationService`).
* Дотримання вимоги безпеки `NFR-04` (заборона зберігання карткових даних та CVV у власній БД, HTTPS TLS 1.3).
* Відсутність циклічних залежностей і прямого доступу UI до бази даних.
* Нативний рендер діаграми на GitHub без необхідності підтримувати окремі бінарні зображення.

## Considered Options
1. **Шаруватий модульний моноліт (5 шарів) + доменна декомпозиція сервісів і репозиторіїв у нотації Mermaid `flowchart TB` із вузлами-портами `([I...])` (Обрано):**
   * *Плюси:* прямий мапінг кожного репозиторію на таблиці `er_v2.mmd`; чітка межа системи (`PaymentGateway` і `SMS / Email Provider` винесені назовні, `AuthService` усередині на базі `User`); нативний рендер на GitHub.
   * *Мінуси:* порт-вузли інтерфейсів вимагають явних підписів `provide`/`require` замість класичних UML-«льодяників».
2. **Укрупнена монолітна модель (об'єднані сервіси каталогу/доставки + зовнішній OAuth) у PlantUML:**
   * *Плюси:* компактніша схема та класичний UML-синтаксис інтерфейсів.
   * *Мінуси:* змішування непов'язаних доменів (меню та кур'єрська доставка), суперечність таблиці `User` через непідтверджений OAuth, необхідність ручного експорту PNG/SVG для GitHub.
3. **Мікросервісна архітектура з окремою БД на кожен сервіс:**
   * *Плюси:* незалежне масштабування сервісів.
   * *Мінуси:* руйнує цілісну реляційну схему `er_v2.mmd` із зовнішніми ключами (`Order` ↔ `User`, `MenuItem`, `Courier`) і створює надлишкову складність для поточного обсягу системи.

## Decision
Обрано **Варіант 1**:
* Внутрішня структура поділена на 5 шарів (`UI → API Gateway → Services → Data Access → PostgreSQL`) із суворо односпрямованими залежностями зверху вниз через явні `provided`/`required`-інтерфейси.
* Поза межею системи (`System Boundary: FoodDelivery`) винесено лише підтверджені вимогами зовнішні інтеграції: `PaymentGateway` (`IPaymentGateway`) та `SMS / Email Provider` (`INotificationGateway`).
* Для діаграми використано єдину нотацію Mermaid `flowchart TB`.

## Consequences
* **Позитивні:** кожен компонент і інтерфейс однозначно трасується до артефактів Завдань 1–4; виключено прямий доступ UI до БД і зберігання платіжних реквізитів усередині системи.
* **Негативні / компроміси:** при подальшому розширенні системи (наприклад, додаванні трекінгу кур'єрів на карті в реальному часі) знадобиться винесення зовнішнього Maps/Geo API за межу системи окремим ADR.
