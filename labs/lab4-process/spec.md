# Специфікація процесу оформлення та оплати замовлення (`UC_Checkout`)

## 1. Мета, нотація та межі процесу
Змоделювати бізнес-процес оформлення й оплати замовлення (`UC_Checkout`, сценарії `SC-01`–`SC-04`, вимоги `FR-01`–`FR-08`, `NFR-02`) у вигляді UML Activity Diagram у нотації **Mermaid `flowchart TD`** (обрано замість BPMN та машини станів через легку підтримку в Git і наочність паралельних потоків; детальніше — у `adr/01-diagram-notation.md`).

* **Учасники (доріжки `subgraph`):** `Client` (клієнт), `OrderSystem` (система замовлень), `PaymentGateway` (зовнішній платіжний шлюз), `RestaurantManager` (менеджер ресторану).
* **Поза обсягом (`Out of Scope`):** автентифікація (`UC_Login`), перегляд меню (`UC_ViewMenu`), внутрішня банківська обробка картки (CVV, 3D-Secure) та доставка кур'єром (`UC_TakeDelivery`).

## 2. Потік кроків та сценарії (`SC-01`–`SC-04`)
1. **Перевірка кошика та адреси (`SC-04`, `FR-01`):** після натискання кнопки оформлення `OrderSystem` перевіряє, чи не порожній кошик, а потім — чи вказано адресу доставки. Якщо кошик порожній або адресу не обрано — виводиться підказка клієнту, процес завершується без звернення до платіжного шлюзу.
2. **Розрахунок суми та промокод (`SC-02`, `FR-02`, `FR-03`):** система зберігає адресу доставки й перевіряє наявність промокоду. Якщо код введено — перевіряється активна акція за `Promotion.name` (термін `activeUntil`) та реферальний зв'язок у `Friendship`; для дійсного коду застосовується знижка 5% і фіксується `Order.promoCode`. Усі три гілки (без коду, зі знижкою 5%, недійсний код) сходяться через вузол злиття (`Merge`) до фіксації підсумкової суми.
3. **Оплата та системний таймер 15 с (`SC-01`, `SC-03`, `NFR-02`):** `OrderSystem` надсилає запит на оплату до `PaymentGateway` і запускає власний таймер очікування **15 секунд**:
   * **Підтвердження (`APPROVED`, `FR-04`–`FR-06`):** система переводить замовлення у статус «Оплачено» та через `Fork` без очікування відповіді паралельно надсилає сповіщення менеджеру й клієнту. У доріжках отримувачів відображається лише прийом події (`Accept`), після чого гілки сходяться у `Join` і процес завершується.
   * **Відмова (`DECLINED`, `FR-07`, `FR-08`) або таймер 15 с (`NFR-02`):** система залишає замовлення у статусі «Чернетка» зі збереженням страв у кошику, не сповіщає менеджера, показує помилку з кнопкою повтору й завершує процес ациклічно.

## 3. Реєстр повідомлень процесу
| Повідомлення (Сигнал) | Відправник → Отримувач | Реакція на відповідь / відсутність відповіді |
| :--- | :--- | :--- |
| Запит на оплату (`chargePayment`) | `OrderSystem` → `PaymentGateway` | `APPROVED` → статус «Оплачено» і `Fork`; `DECLINED` або **таймер 15 с** → збереження «Чернетки» + помилка клієнту |
| Сповіщення ресторану (`notifyRestaurantManager`) | `OrderSystem` → `RestaurantManager` | Надсилається асинхронно через `Fork`; процес іде до `Join` без очікування ручної відповіді |
| Підтвердження оплати (`sendPaymentConfirmation`) | `OrderSystem` → `Client` | Надсилається асинхронно через `Fork`; після `Join` процес успішно завершується |

## 4. Узгодженість із попередніми завданнями
Усі дії описано мовою процесу без програмних викликів. На відміну від Sequence-діаграм Завдання 3 (де сповіщення йшли послідовно й синхронно без гілки таймауту), модель процесу враховує неблокуючу паралельну розсилку (`Fork`/`Join`) та системний таймаут 15 с за `NFR-02`.
